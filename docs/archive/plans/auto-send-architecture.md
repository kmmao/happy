# AutoSend Architecture

> 最后更新：2026-05-13  
> 适用版本：happy-app ≥ 2.26.0

## 功能简介

AutoSend（自动发送）让 Happy 能在用户不手动操作的情况下，根据 AI 建议的下一步选项自动倒计时后发送。其工作流程为：

1. Claude 回复后，系统识别出推荐的下一步操作
2. 倒计时 15 秒，用户可查看或取消
3. 倒计时结束后自动发送，驱动会话继续前进

---

## 模块结构

```
SessionView.tsx (UI 层)
  ├─ useLatestOptions()             # 从消息解析 <options> blocks
  ├─ autoOptionSendService.*        # 触发 LLM 调用
  └─ autoOptionSend state           # 订阅倒计时/推荐项状态

autoOptionSendService.ts (Service Singleton)
  ├─ 状态机执行（checkAndDispatch → reduceAutoOptionSendEvent）
  ├─ 倒计时管理（startTimer → fireTimerFinished）
  └─ 4 条 LLM 路径

autoOptionSend.ts (纯函数状态机)
  ├─ reduceAutoOptionSendEvent
  ├─ buildAutoOptionCandidate / isContextReady / canFire
  └─ rankAndSelectOptions

buildOptionScoringContext.ts
  └─ 构建发给 LLM 的上下文摘要

happy-server
  ├─ /v1/options/score  → optionScorer.ts
  └─ /v1/options/generate → optionGenerator.ts
```

## 状态机

```
off ←─────────── toggle(false)
 │
 └─ toggle(true) → idle ←─── context-invalidated
                    │              ↑
            options-updated        │（输入框非空/切会话/stale/AskUserQuestion）
            + isContextReady       │
            + candidate 非 null    │
                    │              │
                    ▼              │
                  armed ─── 15s → ready
                    │                │
          triggerSemanticScoring   attempt-fire
          (LLM 重新排名)              │
                                 canFire? ──Yes→ 发送
                                          └─No──→ idle
```

### `isContextReady` 检查项

- `context.snapshot` 非 null
- `!hasAskUserQuestionVisible`
- `session.active === true`
- `sessionId === currentSessionId`
- `inputText.trim() === ""`
- `!hasPendingImages && !isSttListening`

### `canFire` 检查项（`autoOptionSend.ts`）

- `state.candidate` 非 null
- `isContextReady` 通过
- `buildAutoOptionCandidate(context)` 非 null
- `candidate.optionsHash === state.candidate.optionsHash`
- `context.snapshot.sourceMessageId === state.candidate.sourceMessageId`
- `lastAutoSentKey !== buildAutoSentKey(state.candidate)`

> ⚠️ `recommendedText` 的相等性检查已被移除（v2.26.0），原因：LLM scoring 会在倒计时中更新推荐项，但 `canFire` 里的 `buildAutoOptionCandidate` 不含语义分，导致比较结果不一致而静默失败。

## 4 条 LLM 路径

### 触发条件与冷却

| 路径 | 触发点 | 去重（主要） | 冷却（次要） |
|------|-------|------------|------------|
| **Auto-send Scoring** | 状态进入 `armed` | `semanticScores` hash 缓存（永久/内存） | 30s `lastSemanticScoredAt` |
| **Passive Scoring** | SessionView `useEffect`（items≥2） | 同上 | 30s `lastPassiveScoredAt` |
| **Auto-send Generation** | `checkAndDispatch`（无 markdown options，auto-send 开启） | `lastAutoGeneratedTurnId` per turn | 10s `lastGeneratedAt` |
| **Passive Generation** | SessionView `useEffect`（items=0） | `lastGeneratedTurnId` per turn | 5s `lastPassiveGeneratedAt` |

### 独立 Controller Map

两条 Generation 路径使用独立的 AbortController，互不干扰：

| 路径 | Controller Map |
|------|---------------|
| Auto-send Generation | `autoGenerationControllers` |
| Passive Generation | `generationControllers` |

## Options 来源

### 优先级

```
1. Claude 回复中的 <options> blocks（markdown options）
   ← parseMarkdown → useLatestOptions → latestOptions.items[]

2. LLM 主动生成（fallback，当 markdown options 不存在时）
   ← triggerOptionGeneration / triggerGenerationIfNeeded
   → POST /v1/options/generate
   → generatedOptions Map（内存）
```

### Markdown Options 格式

Claude 回复必须包含如下格式（单行，不支持多行）：

```
<options>
<option>选项文本A</option>
<option>选项文本B</option>
<option>选项文本C</option>
</options>
```

解析逻辑：`parseMarkdownBlock.ts:186`，按行扫描，正则 `/<option>(.*?)<\/option>/` 提取。

### 生成 Options 的上下文

`buildOptionScoringContext()` 生成发给 LLM 的摘要，结构如下（总长度≤1800字）：

```
Task: <session 标题，最多100字>           # 来自 metadata.displayName 或 summary.text
Goal: <会话第一条用户消息，最多250字>      # 仅当总轮次 > 3 时追加，防止与 Recent 重复
Recent:
  U: <用户消息，最多150字>
  A: <Agent 回复，最多200字>              # 最近 3 轮，时间正序
  ...
```

## 数据流：从 Claude 回复到自动发送

```
Claude 回复
│
├─[含 <options>]─→ latestOptions.items[n]
│                        │
│              latestOptionsHash 变化
│                        │
│                SessionView useEffect
│                   triggerScoringIfNeeded()
│                        │
│                POST /v1/options/score
│                        │
│               semanticScores 更新
│                        │
│                onReady → checkAndDispatch
│                → armed（markdown candidate）
│
└─[不含 <options>]─→ latestOptions.items = []
                          │
             ┌────────────┴────────────┐
             │                        │
   useEffect: triggerGenerationIfNeeded   onReady: triggerOptionGeneration
   (passive, 5s cooldown)              (auto-send, 10s cooldown)
             │                        │
             └────────────┬────────────┘
                          │
               POST /v1/options/generate
                          │
              generatedOptions.set(sessionId, items[])
                          │
                    checkAndDispatch
                    → snapshot from generatedOptions (sourceMessageId=null)
                    → armed（generated candidate）
                    → startTimer(15s)
                    → triggerSemanticScoring
                          │
              timer-finished → canFire? → sendMessage(recommendedText)
```

## 边界场景处理

### 已发过同一 Options 后的行为

发送后 `lastAutoSentKey = hash:sourceId`，下次同样的 options 不会再 arm。  
**新用户消息到来时清除**（`onMessages` 里检测到 `user-text` → `lastAutoSentKey = null`），确保新一轮 AI 回复可以重新 arm。

### 倒计时中 Claude 给出新回复

- 新回复含 options：`onMessages` → context-invalidated → idle → `onReady` → 新 candidate → 重新 arm（倒计时重置）
- 新回复不含 options：同上，idle 后触发新一轮生成

### 跨 Tab 防重复发送

- `BroadcastChannel` 通知其他 tab 取消倒计时
- `localStorage` 悲观锁（TTL=30s）防并发双发
- 注：锁的 read→write 非原子，极低概率双发（已知，注释标注）

### sync 认证竞争（页面冷启动）

页面加载时 `sync.credentials` 可能尚未就绪，`useEffect` 首次运行时 LLM 调用会因 `credentials=null` 而 return。  
**已修复**：SessionView useEffect 在 3 秒后执行一次 retry，确保 sync 认证完成后重新触发。

## 消息来源标识

### Auto-sent 消息的视觉标记

auto-send 发出的消息气泡右下角显示 `✨ Auto-sent`（各语言本地化）。

**实现机制**：
- `sync.sendMessage()` 调用时传入 `options.source = "auto-option-send"`
- 该值写入 `message.meta.source`（`typesMessageMeta.ts` 的 Zod schema 已定义）
- `MessageView.tsx` 的 `UserTextBlock` 检测 `message.meta?.source === "auto-option-send"`
- 匹配时在气泡内渲染 badge：`<Ionicons name="sparkles" />` + i18n key `session.autoSent`

**关键文件**：
- `sync/typesMessageMeta.ts` — `source: z.enum(["auto-option-send"])` 字段定义
- `sync/sync.ts:787` — `...(options?.source && { source: options.source })` 写入 meta
- `components/MessageView.tsx` — `UserTextBlock` 渲染逻辑 + `autoSentBadge` 样式
- `text/translations/*.ts` — `session.autoSent` key（10 个语言）

**用户识别效果**：

## 推荐选项的确定机制

### 时序问题与修复

auto-send 的推荐选项由两个阶段决定：

1. **Arm 时（heuristic）**：`buildAutoOptionCandidate` 调用 `rankAndSelectOptions(items, statsResolver, contextKeywords)`，无语义分，结果写入 `state.candidate.recommendedText`

2. **LLM Scoring 返回后（semantic）**：`triggerSemanticScoring` 的 `.then()` 回调更新 `state.candidate.recommendedText` 为语义分最高的选项

3. **Fire 时（final check）**：`fireTimerFinished` 在发送前检查 `semanticScores`，若已就绪则用 `rankAndSelectOptions(items, undefined, undefined, semanticScores)` 重新确定最优推荐，覆盖可能落后的 heuristic 结果

这确保即使 LLM scoring 在 15s 倒计时结束前才返回，auto-send 也能发送语义分最高的选项，而不是启动时的 heuristic 推荐。
