# World Model：Happy 的终极愿景

_Created: 2026-04-06_
_Status: 历史愿景参考_

> **历史参考说明**：本文保留早期 World Model 的概念隐喻和能力设想，其中“项目是世界 / 一个项目 = 一个世界”已不再作为当前重构方向。当前主设计锚点见 [全局 World Model UI 与结构重构方案](./global-world-model-ui-restructure.md)：Happy 当前承载一个主世界，项目只是世界中的事件来源、上下文节点或任务链组成部分；World 还需要预留外部世界接入点，未来形成 Universe / Multiverse。

## 核心理念

**历史隐喻：用户是上帝，项目是世界，Agent 是居民。**

> 命名边界规范见：[world-project-naming-guideline.md](./world-project-naming-guideline.md)

传统模式下，AI Agent 是被动执行器——人类发指令，Agent 跑一次，返回结果。Happy 要实现的是一种根本性的转变：

- **声明式而非命令式**：你描述"世界应该是什么样"，而不是"做什么"
- **持续运行而非一次性**：Agent 不是工具，是世界里的居民，持续存在、持续工作
- **自主决策而非等待指令**：Agent 根据法则和目标自行判断该做什么

类比：Kubernetes 不告诉容器"启动、停止、重启"，它说"我要 3 个副本在线"，控制器自己搞定。Happy 的 World Model 对项目做同样的事。

## 概念模型

### 历史假设：一个项目 = 一个世界 (World)

> 这是 2026-04-06 的早期业务语义映射，已降级为历史参考。当前重构方向不再把 Project 视为 World 边界；Project 只是全局主世界中的事件来源、上下文节点或任务链组成部分。

```
World {
  identity     → 这个世界是什么（项目愿景、定位）
  narrative    → 当前的叙事（阶段目标、方向）
  laws         → 世界法则（持续约束、不可违反）
  agents       → 居民（不同角色、不同职责）
  knowledge    → 世界的记忆（积累的知识和判例）
  history      → 世界的历史（事件时间线）
}
```

### 上帝的三种操作

| 操作 | 含义 | 系统反应 |
|------|------|---------|
| **立法** | 增删改法则（laws） | 所有 Agent 重新评估当前状态，发现违规则自动修复 |
| **叙事** | 设定/修改阶段目标 | 规划者 Agent 分解目标为任务，分配给合适的角色 |
| **裁决** | 对 Agent 上报的不确定决策做选择 | 决策记入知识库成为判例法，同类问题不再上报 |

**关键约束**：上帝不写代码、不分配任务、不审 PR。只管立法、叙事和裁决。

## 世界法则 (Laws)

法则是世界的"物理定律"——Agent 必须遵守的持续性约束。

### 法则分类

| 类型 | 举例 | 检测方式 |
|------|------|---------|
| **质量法则** | 测试覆盖率 ≥ 80% | Supervisor 定期扫描 |
| **安全法则** | 无已知漏洞超过 24h | 依赖扫描 + CVE 监控 |
| **流程法则** | PR 不超过 400 行 | Webhook 检查 |
| **架构法则** | 所有 API 必须有 rate limiting | 代码分析 |
| **运维法则** | 构建时间不超过 5 分钟 | CI 监控 |

### 法则的生命周期

```
草案 → 生效 → [违规检测] → [自动修复 or 上报裁决]
                ↓
              暂停（特殊时期，如 release freeze）
                ↓
              废止（不再适用）
```

法则不是一成不变的。上帝可以随时暂停、修改或废止法则。

## Agent 角色系统

### 预定义角色

| 角色 | 隐喻 | 职责 | 触发方式 | 对应现有系统 |
|------|------|------|---------|-------------|
| **守卫 (Guardian)** | 城门守卫 | 安全扫描、依赖更新、法则合规检查 | 定时 + 事件 | Supervisor（安全类） |
| **建筑师 (Builder)** | 建筑工人 | 执行目标分解出的功能开发任务 | 目标分配 | Task Queue |
| **医生 (Healer)** | 驻城医师 | 健康监控、Bug 修复、性能优化 | 定时 + 告警 | Supervisor（修复类） |
| **史官 (Chronicler)** | 记录者 | 维护知识库、写变更日志、总结经验 | 事件 + 定时 | Knowledge 生命周期 |
| **规划者 (Planner)** | 军师 | 目标分解、任务排期、风险评估 | 叙事变更 | 新增 |
| **信使 (Messenger)** | 传令官 | Agent 间通信协调、冲突仲裁 | 冲突检测 | 新增 |

### 角色 vs 现有系统的映射

```
现有系统                    → World Model 角色
────────                    ─────────────────
Supervisor (分析模式)       → 守卫 + 医生
Supervisor (修复模式)       → 医生
Agent Loop                  → 可配置为任意角色
Task Queue                  → 建筑师的工作队列
Knowledge 生命周期          → 史官的职责
Cron Trigger               → 角色的心跳机制
Webhook Trigger            → 角色的事件感知
```

### 角色的独立性

每个角色是一个独立的 Agent 实例，拥有：
- **身份**：名称、角色类型、自定义指令
- **技能**：绑定的 Skills 集合
- **记忆**：可访问的 Knowledge 子集
- **权限**：可执行的操作范围（如建筑师可以提 PR，守卫只能报告）
- **并发上限**：同时运行的最大任务数
- **状态**：idle / working / blocked / sleeping

## 裁决机制 (Adjudication)

当 Agent 遇到不确定的决策时，不自作主张，而是上报给上帝裁决。

### 触发条件

- Agent 信心度 < 阈值（如 70%）
- 涉及法则冲突（两条法则互相矛盾）
- 涉及架构变更（超出 Agent 权限）
- 多个 Agent 对同一问题有不同建议

### 裁决流程

```
Agent 发现不确定问题
  ↓
创建 Decision 请求（包含问题描述 + 选项 + 各选项利弊）
  ↓
推送到 Inbox（高优先级）
  ↓
上帝选择选项 + 可选地写明理由
  ↓
决策执行 + 结果记入 Knowledge Base
  ↓
同类问题下次 Agent 直接参考判例，不再上报
```

### 判例法效应

裁决不是一次性的。每个裁决都成为知识库中的"判例"，Agent 在后续遇到类似情况时可以引用。随着判例积累，需要上帝裁决的事情越来越少——**世界逐渐自治**。

## 目标分解引擎

上帝设定的"叙事"（阶段目标）需要被分解成可执行的任务。

### 分解流程

```
上帝设定目标："本周完成 OAuth2 集成"
  ↓
规划者 Agent 分析目标
  ↓
生成任务树：
  ├─ 调研 OAuth2 方案选型（规划者自行完成）
  ├─ 设计数据库 schema 变更（规划者 → 上报裁决 if 多方案）
  ├─ 实现 OAuth2 provider 集成（分配给建筑师）
  ├─ 编写集成测试（分配给建筑师）
  ├─ 安全审查（分配给守卫）
  └─ 更新 API 文档（分配给史官）
  ↓
任务进入各角色的工作队列
  ↓
各角色按优先级自主执行
  ↓
进度汇总到上帝的 Dashboard
```

### 目标状态追踪

```
Goal {
  title: "完成 OAuth2 集成"
  status: planning | in_progress | blocked | completed
  progress: 0-100%
  tasks: Task[]           // 分解出的任务
  blockers: Decision[]    // 待裁决的问题
  deadline: Date?         // 可选截止日期
}
```

## 世界间隔离

每个项目（世界）完全自成一体：

- **独立法则**：不同项目有不同的质量标准、流程规范
- **独立角色**：每个世界的 Agent 配置独立
- **独立知识**：Knowledge Base 按项目隔离
- **独立历史**：事件时间线按项目独立
- **独立资源**：成本上限、并发上限按项目配置

跨世界共享的只有：
- 全局 Skills（通用能力）
- 全局法则模板（可选继承）
- 账户级别的资源配额

## 与 Multica 的本质区别

| 维度 | Multica | Happy World Model |
|------|---------|-------------------|
| **核心隐喻** | 团队管理（Linear 替代品） | 世界治理（上帝模式） |
| **Agent 自主性** | 从 Issue 池捞任务 | 根据法则和目标自主判断 |
| **人类角色** | 项目经理（分配任务） | 立法者（定义规则） |
| **知识管理** | 基础 pgvector | 病历系统 + 判例法 + 生命周期 |
| **安全** | 明文传输 | E2E 加密 |
| **进化方向** | Agent 越来越像好员工 | 世界越来越自治（判例积累） |

**Multica 的终态**是"Agent 是好员工"——你还是得管理它们。
**Happy 的终态**是"世界自治"——判例积累到一定程度后，上帝基本不用干预。

## 不做什么

以下方向明确排除或推迟：

- **区块链存储**：PostgreSQL + E2E 加密已满足"不灭"需求，区块链增加复杂度无实际收益
- **元宇宙可视化**：核心模型跑通后可以考虑，现阶段是锦上添花
- **跨世界 Agent 共享**：初期每个世界独立，避免引入复杂的权限和上下文隔离问题
- **自然语言法则引擎**：初期法则用结构化定义，不做自然语言到规则的自动转换
