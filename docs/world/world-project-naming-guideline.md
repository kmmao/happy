# Project 与 World 命名边界规范

_Created: 2026-04-07_  
_Status: 生效中_

## 目标

在引入 World Model 后，统一「技术实现」与「业务语义」的命名策略，避免无差别重命名带来的高风险迁移。

## 决策标准

- **技术归属 / 基础承载层**：使用 `project`
- **世界治理 / 用户心智层**：使用 `world`

一句话：**World belongs to Project**，World 是 Project 之上的语义层，而不是替代 Project 的底层模型。

## 保留 `project` 的范围（不做全量重命名）

- 数据库主模型与关联键（如 `Project`, `projectId`）
- 主资源路由（如 `/projects/:id/...`）
- 核心同步实体与权限归属链路
- 内部实现中与跨模块兼容强耦合的标识符

## 优先转为 `world` 的范围（低风险优先）

- World 功能域的用户可见文案（叙事、法则、角色、目标、裁决）
- World 入口页与相关按钮、提示、引导语
- 世界治理相关统计与状态说明
- 对外展示层可读字段（必要时加别名，不破坏底层字段）

## 迁移策略

1. **先文案后模型**：先统一用户可见语义，再评估是否需要接口别名。
2. **保持向后兼容**：底层继续使用 `projectId`，避免一次性数据迁移。
3. **按风险分层推进**：
   - L1（低风险）：UI 文案、帮助文档、提示文案
   - L2（中风险）：API 响应别名、前端类型别名
   - L3（高风险）：数据库字段/路由主资源重命名（默认不做）

## 本规范的执行要求

- 新增 World 相关功能时，先判断是「承载层」还是「治理层」，再定命名。
- 代码评审时，命名一致性作为必查项。
- 若出现歧义，按"用户是否直接感知该术语"优先判断：
  - 用户直接感知：优先 `world`
  - 仅内部实现：优先 `project`

## 长期定位（终态）

**世界是项目的"人格"，不是项目的"替身"。**

- **用户心智层完全世界化**：App UI、帮助文档、提示文案、Agent 提示词全部使用 `world` 语义。
- **技术层永远保持 Project**：数据库、API 路由、CLI flag、同步实体一律使用 `project`。
- **这不是过渡方案，这就是终态。**

### 为什么不做完全替换

1. **Project 是客观存在，World 是主观赋义**：用户可以关联一个仓库（Project）但从不设定叙事/法则，此时"空世界"概念不成立，而"空项目"是正常状态。
2. **全量重命名的代价远大于收益**：影响数十张表、所有外键、所有已发布 API 与 CLI 参数，破坏向后兼容。
3. **分层是自然的**：底层容器用 `project`，上层治理用 `world`，两者共存而非替代——与 Kubernetes 的 Pod/Deployment 分层同理。

### 未来演进方向

- 如果后续需要"多世界共享一个仓库"或"一个世界跨多个仓库"，届时新建 `World` 数据模型并关联 `Project`，当前命名策略无需变动。

## 组件/文件命名规则

组件名和文件名跟随其**所属功能域**，而非数据源：

- 世界治理功能的组件使用 `World` 前缀（如 `WorldOverviewTab`、`WorldRolesTab`、`WorldGoalsTab`）
- 项目管理功能的组件使用 `Project` 前缀（如 `ProjectDetailView`、`ProjectProfileCard`）
- Props 中传递 `project` 对象是正常的（数据源来自承载层），不需要重命名为 `world`
- 路由文件路径保留 `project`（如 `project/[id]/world-laws.tsx`），因为路由路径属承载层

## 防漂移规则

1. **同一能力的多入口模板必须复用同一文案源**，避免手动模板 vs 一键生成措辞不一致。
2. **世界域词汇表**（narrative → 世界叙事、laws → 世界法则、roles → 世界角色、goals → 世界目标、decisions → 世界裁决）在 i18n 中保持统一。
3. **PR checklist 必查项**：世界功能域文案不得出现 `project`；承载层代码不得出现 `world` 作为变量/模型名。
